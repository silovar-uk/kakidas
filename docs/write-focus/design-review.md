# kakidas v0.8.1｜「書く」の視覚階層再設計（守破離）

## Executive decision

**次に目立たせるべきはボタンでも欄の名前でもなく、「いま文字を入力できる場所」。**

v0.8.1では書き口が `DeskSlot` を通じて3つの欄へ移動するため、固定位置だけに派手な色を塗ると実際の編集位置と食い違う。入力対象の実DOM `.desk-host` を起点に、フォーカスの移動に合わせて明度が追従するUIへ変更する。周囲の本文は半透明にしない。

## 現状の一次情報

- `src/styles-togu.css`：`--color-paper: #f4f2ed`、`--color-sheet: #fffdf9`。各欄は原則transparentで、見出し罫が黒に近い。
- `src/styles-amu.css`：PCの書き口の背景はtransparent、枠は消す設計。補助ボタンは省略表示。
- `src/components/DeskSlot.tsx`：実DOM `.desk-host` をアクティブな欄へ移す。同一textareaのフォーカスを維持する。
- `src/pages/MemoEditorPage.tsx`：PCは`deskSlot`、モバイルは`activeKind`を使用。保存処理・IME処理は本変更では触らない。

## 3名によるレビュー

### 前提を疑う担当

単純に「その他を薄い文字にする」のは誤り。読むために保存した一覧の本文まで薄くすると、編集・推敲・引用の品質が下がる。差を生むのは色の濃さではなく、**面の段差・余白・状態の対応**。全欄を均等に主張させる構造を改める。

反証：書き口が判別しやすくなっても、保存した項目を読むのが遅くなるなら本案を却下。

### リサーチ担当

- W3C WCAG 2.2 §1.4.3：通常テキストのコントラストは原則4.5:1以上。文字色を薄くして見えなくする対処は避ける。
  https://www.w3.org/TR/WCAG22/#contrast-minimum
- W3C WCAG 2.2 §1.4.11：必要なUI状態の視覚識別は原則3:1以上。現在位置の強調を面の色だけに依存させず、朱色の左罫線も併用する。
  https://www.w3.org/TR/WCAG22/#non-text-contrast
- Nielsen Norman Group、Visual Hierarchy in UX：コントラスト・大きさ・グルーピングで読む順番を設計し、同等の強調を増やさない。
  https://www.nngroup.com/articles/visual-hierarchy-ux-definition/
- Nielsen Norman Group、Progressive Disclosure：必要な操作を前面に、頻度の低い操作を次段に置く。
  https://www.nngroup.com/articles/progressive-disclosure/

### 実装手順を組み立てる担当

データ・レイアウト・キー操作を変える前に、スタイルだけで「入力の現在地」を強調する。

| 役割 | 背景・文字 | 狙い |
|---|---|---|
| 書き口 | `#fffefa` + 囲まない白い面 + 通常は淡い一本線、フォーカス時のみ朱色の左罫 | どこへ書くか即座に分かる |
| 書き口がいる欄 | `#faf9f6` | 入力との連続性を示す |
| それ以外の欄 | `#f6f5f2`、本文`#625e57` | 一段退かせつつ可読性を保つ |
| 補助ボタン・見出し | `#6b675f`、薄い罫線 | 行動選択の雑音を減らす |
| エラー・選択・重要な操作 | 従来の状態色を維持 | 意味が変わらない |

## 守破離

- **守**：Meiryoや既存の「紙・墨・朱」の世界観、可動するDeskSlot、自動保存、清書、モバイル操作、キーボード操作を維持。
- **破**：全3列が同じ濃度である必要はない。入力中の列以外の面とヘッダー罫を薄くし、テキストは読み取れる濃さを維持。
- **離**：『静かなスポットライト』。画面をタップした先へ**光（明るさ）が追従**する。追加のスイッチや操作は不要。デスクトップの書き口移動にDOM CSSで追従する。

## UIの代替案と採用理由

| 案 | 利点 | 弱点 | 判断 |
|---|---|---|---|
| A 色だけ調整 | 最小リスク | 状態が変わっても見え方が変わらない | 単独採用は不十分 |
| B 3列構造そのものを改修 | 表示面積を最大化 | v0.8.1の新設計・既存データへの影響が大きい | 現段階で見送り |
| C 可動書き口に光が追従 | 現在地が明確で既存構造を活用 | 状態に応じた配色QAが必要 | **Aと組み合わせて今回採用** |

## 受け入れ基準

1. PCで書き口がアウトライン→段落へ移動しても、明るい列と書き口が一致。
2. 375/768/921/1366pxで文字やボタンが切れず、横スクロールなし。
3. 本文と書き口のテキストコントラストが4.5:1以上。
4. 選択・フォーカス・保存・完了・エラーの状態色を保持。
5. 既存P1-P3、amu、outline、shitate、toguのQAに退行なし。
6. 実際のiPhone Safariで、キーボード表示中の位置と配色を目視確認（CIでは代替できない）。

未実施の実機確認、利用者の視線移動や入力開始時間の差については、改善済みと断定しない。

## 次フェーズの計画

- **今：薄くする**　色・背景・罫を3段階にし、CIで実測。元に戻せるCSS単位のPRで実施。
- **次：隠す**　補助コントロールを、キーボード入力を阻害しない範囲で、必要なタイミングだけ表示。表示・非表示によるレイアウトシフトを測定。
- **その次：育てる**　入力中のアウトライン項目と関連段落・参考URLだけが自然に浮かぶ「編むレンズ」を、実データを変えず試作。必要性は利用行動から判断。

成果判断はスクリーンショットの好みだけでなく、書く場所の発見時間、誤クリック数、保存済み本文の読解速度、実機タップ・コントラストをもとに行う。
