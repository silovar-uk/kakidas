# kakidas NEXT｜P0実証・本実装判断レポート

評価基準日：2026年10月16日（日本時間）  
対象：`silovar-uk/kakidas` 本番 `main` v0.7.1（`f44a9c4913de55fc8ca30698e64229ad59dcde9b`）と、実験 PR [#15](https://github.com/silovar-uk/kakidas/pull/15) の独立P0版。  
**総合判断：P0の検証継続はGO。本番の既存アウトライナーの置換はNO-GO。**

## 0. 判断の要旨

1. **技術的成立性**：P0の行内編集、連続入力、字下げ、枝移動、Undo/Redo、葉ノードへの集中表示について、自動ブラウザー試験14/14合格。今回追加した乱数シード24種類×45操作＝1,080ステップの木構造不変条件検査でも違反ゼロ（状態変更660回、GitHub Actions [38762680175](https://github.com/silovar-uk/kakidas/actions/runs/38762680175)）。
2. **優位性の未証明**：本番v0.7.1にも、上部書き口を使った連続Enter保存は既に存在する。「P0は30行入力できる」だけでは現行より優位といえない。P0が改善するという仮説を判定すべき主なタスクは、**既存の枝を再構成する作業、選択・編集・操作の連続性、集中と復帰**である。
3. **機能比較の不均等性**：P0には、本番の段落、参考URL、タグ、備考、清書、IndexedDB・Supabase同期に相当する機能が存在しない。これらのタスクで両UIの所要時間を直接比較することは不公平。未対応は「実装差・適用範囲の制約」として明示する。
4. **成果の質は未測定**：人間の参加者による操作、作成された文章・アウトラインを独立評価者が採点した結果、物理iPhone Safari／日本語IME実機の記録はいずれもまだない。AIが参加者・評価者を仮想生成して補うことはしない。

## 2. 一流の専門家なら、さらに何を疑うか

### 2.1 「入力の主役をアウトラインへ移す」ことの副作用
- 行内編集のために常時textareaを並べると、スクリーンリーダーやTabナビゲーションの負荷は増えないか。
- 先に構造を意識させると、まだ分類できない思いつきの記録が遅くならないか。
- 文章の再編成で便利な編集は、引用・長文・参照URLを入れる段階で負担にならないか。
- 「行の入れ替え」は速くなっても、実際の**論理の再構成**がうまくなるか。
- Undo/Redoの期待する単位は「一打鍵」「一行の確定」「一枝の移動」「同期された変更」のどれか。異なる単位を混ぜた際に誤解はないか。

### 2.2 テストで簡単に見落とすリスク
- 同じ7行の初期モデルでのランダム操作は、深い階層・大きい枝・極端な兄弟数を網羅していない。
- `localStorage`への保存が成功したことは、IndexedDBの原子的保存やクラウド競合処理の代わりにならない。
- DOM合成イベントの`isComposing`は、端末内の日本語変換確定・候補選択・キーボードの実際の挙動を代替しない。
- P0のUndo履歴はメモリ上の最大100件で、再読込では復元されない。これは仕様上の制約だが、正式版の利用者期待を満たすか未検証。
- オンボーディング前と慣れた後の効果は別。キーボード熟練者の結果を全利用者へ一般化しない。

## 3. 調査基準と再調査

- [Workflowy公式：Bullet list](https://workflowy.com/help/bullets/)：Enter、Tab、子を持つ枝の移動。
- [Workflowy公式：Navigate around](https://workflowy.com/help/navigate-around)：bulletのZoomと矢印の折りたたみを区別する。
- [Dynalist公式：Keyboard shortcut reference](https://help.dynalist.io/article/91-keyboard-shortcut-reference)：字下げ、Undo/Redo、項目の選択と移動を体系化。日本語を含むキーボード配列差の注意もある。
- [RemNote公式：Outlines and Terminology](https://help.remnote.com/en/articles/8196578-outlines-and-terminology)：字上げで既存の親子関係を意図せず変えない設計を明示。
- [W3C WAI-ARIA APG：Tree View](https://www.w3.org/WAI/ARIA/apg/patterns/treeview/)、[Keyboard Interface](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/)：フォーカス、選択、Tab、矢印キー。
- [ISO 9241-11:2018](https://www.iso.org/standard/63500.html)：有効さ・効率・満足度という利用状況に依存した枠組み。規格自体は特定の実験手順を規定しない。
- [NASA公式 NASA-TLX](https://www.nasa.gov/human-systems-integration-division/nasa-task-load-index-tlx/)：精神的・身体的・時間的要求、遂行度、努力、不満の6次元。**本研究キットの簡易7段階質問はNASA-TLXではない**。
- [NN/g Usability Testing 101](https://www.nngroup.com/articles/usability-testing-101/)：実際の利用者と現実的な課題を重視。少人数は問題発見には使えるが、精密な効果推定とは分ける。

**反証による結論の変更**：初期仮説「連続入力ができるだけでP0が優位」は却下。現行にも連続入力があるため、両版が同等以上の成果を生むか、既存の構造を再編集する場面に研究焦点を移した。

## 4. 検証課題と比較の公平性

| ID | 課題 | A/Bで公平に比較可能か | 主指標 |
|---|---|---|---|
| C1 | 未整理の断片10個を保存 | 概ね可。Aは上部書き口、Bは未整理欄 | 完了／誤操作／時間／主観的負荷 |
| S1 | 4親×3子（16項目）の階層を作成 | 可。ただし入力開始位置・並び順の説明を統一 | 親子一致／操作失敗／時間 |
| S2 | 子3件を持つ枝を別の場所へ移動 | 可。枝全体を保持することを必須とする | 枝の完全性／位置／Undo回数 |
| S3 | 葉ノードへ集中、編集、全体へ戻る | 機能差の検出に適する。Aに同じ意味の機能がない場合、時間で無理に比較しない | 達成可能性／迷い／操作数 |
| D1 | 構造化から段落、参考URL、清書へ展開 | **不可（P0未実装）**。本実装の前提条件として別ゲートで評価 | 機能対応状況／データ互換性 |

実験では、地域マラソン大会と子どもの運動スクールという難易度の近い2題材を用意。参加者コードからAB/BAと題材の順を決定し、練習量をそろえる。計測画面の切替時間が含まれるため、所要時間の精度は限定される。**実験用HTMLは参加者のキー入力・メモ本文を送信しない**。

### 4.1 盲検評価（第三者の判断）

アウトライン完成品をUIや氏名の手掛かりを削除した形式に統一して、2人以上の評価者が独立に採点する。各項目0～4点：

| 指標 | 0点 | 2点 | 4点 |
|---|---|---|---|
| 論点網羅性 | 主要領域がほぼない | 一部抜けがある | 指定領域が十分にそろう |
| 階層一貫性 | 親子関係の意味が破綻 | まれに分類が揺れる | 同じ分類原理で一貫 |
| 論理明瞭性 | 関係が読み取れない | 一部は読み取れる | 見出しから論理を追える |
| 重複抑制 | 多数の重複・混同 | 一部重複 | 重複がなく区別明確 |
| 文章への展開可能性 | 展開困難 | 順序や補足が必要 | そのまま骨子に使える |

1点と3点は両端の中間。評価者の差が2点以上の指標は再協議前の生得点を保持する。全点数の単純合計だけで採否を決めない。

## 5. 追加した機械的な安全検査

実験ブランチに `docs/prototypes/outliner-p0.invariants.mjs` を追加し、HTTP上の試作アプリに対して乱数シード1～24、それぞれ45操作を実行した。

対象操作：字下げ、字上げ、枝の上下移動、項目追加、Undo、Redo。各操作直後に以下を確認する：

1. ノードIDに重複がない。
2. 親IDの参照先が存在する。
3. 親子グラフに循環がない。
4. 親子から再構築した深さ優先順が配列順と一致する。
5. 最後に再読み込みして状態が一致する。

**結果**：24シード・1,080条件確認・660回の実際の状態変化・検出した違反0。従来の専用ブラウザーQAも14/14合格。結果リンク：[GitHub Actions #38762680175](https://github.com/silovar-uk/kakidas/actions/runs/38762680175)。

この検査は「安全性の証明」ではなく「この操作系列では破損を検出しなかった」という結果。開始時の樹形は同じサンプルから発展している。極端な深さ、5000項目、マルチタブ競合、ストレージ障害を代表しない。

## 8. 次に必要な、最少の5つの仕事

**第1優先：人間の比較試験**。まず本人＋実用対象に近い数名で実施し、行内編集の学習負荷、旧版の高速収集を失わないか、枝操作の迷いを観察。少人数では問題発見を目的とし、効果の厳密な割合を推定しない。

**第2優先：完成品の盲検採点**。同じ基準で評価した結果を別シートへ保存し、使いやすさの改善と論理構造の改善を区別する。

**第3優先：iPhone Safari／日本語IME実機**。候補確定、ソフトキーボード、折りたたみ、ズーム、VoiceOver、フォーカス戻り位置の点検。

**第4優先：保存・Undo・同期の設計検証**。本番DBコピーではなく匿名のfixtureでIndexedDBの原子性、複数タブ／衝突、履歴粒度・Undo再実行の整合を試験。

**第5優先：本実装判定**。収集タスクで許容できない悪化がなく、構造化タスクで実質的な改善が観察でき、上記安全ゲートを満たしたら、Reactへ縦切り移植するPRを作る。満たさなければP0設計を修正する。
