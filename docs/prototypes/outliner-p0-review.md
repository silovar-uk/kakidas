# kakidas NEXT｜アウトライナー再設計・P0実証レポート

調査・実装：2026年10月15日  
対象：`silovar-uk/kakidas`、現行 `main` の v0.7.1（基準コミット `f44a9c4913de55fc8ca30698e64229ad59dcde9b`）  
成果物：本番から独立した `public/outliner-lab.html`、ブラウザーQA、比較評価、本実装計画  
**判断：P0試作は有効。既存の本番アウトライナーの全面置換は、まだNO-GO。**

## 1. Executive Summary：何を解決するのか

現在のアプリは「上部書き口→置き先→一覧」で情報を集める設計を維持したまま、一覧に階層操作を追加している。そのため連続入力・階層の試行錯誤のたびに、入力箇所と構造編集の箇所が分かれやすい。真に改善するべきは見た目ではなく**行そのものを編集の中心に置くこと**である。

P0では、既存メモに触れず、独立したHTMLの中で「本文直接編集→Enterで隣の行→Tabで階層化→子を含む枝の移動→何段階も戻す→枝に集中」の一連の流れを実装した。7行の例から30行を継続して追加入力する自動操作を通し、テスト中に発見したフォーカス遅延を修正。これは機械的な操作確認であり、実ユーザーの時間短縮率を証明したものではない。

## 2. 現行コードの再監査（確認した事実）

| 観点 | 現行の具体的な構造 | UX上の含意 |
|---|---|---|
| 入力先 | `EntryComposer.tsx` に上部書き口。`OutlineList.tsx` に別の編集欄 | 書く場所が2つあり、主編集面が曖昧 |
| Enter | アウトライン編集中のEnterは既存項目の保存後に別の新規入力欄を生成 | 連続入力自体は可能だが、エディターの入れ替わりがフォーカス不安定要因 |
| Tab | 編集中のTab/Shift+Tabは保存後の階層変更、選択時のTabも階層化に転用 | 閲覧モードの通常Tab移動と競合し得る |
| ズーム | `OutlineList` は選択ノード自身を配下リストから除外し、子だけ表示 | 葉ノードの単独編集体験が成立しにくい |
| Undo | `MoveHistory` が1個 | 複数の構造変更を連続で巻き戻せない |
| 列と情報モデル | `MemoEditorPage.tsx` でアウトライン、段落、URLを分割 | どの主張にどの段落・根拠が対応するか、ノード基点では見えない |
| 保存データ | `EntryRow` に`id`、`parent_id`、`sort_order`、`kind`などが存在 | 当面はDB移行なしで構造編集モデルを試せる |

## 3. 競合公式資料から抽出した設計原理

| 公式出典 | 確認した操作・概念 | kakidasへの示唆 | 今回の適用 |
|---|---|---|---|
| [Workflowy Bullet list](https://workflowy.com/help/bullets/)・[Navigate around](https://workflowy.com/help/navigate-around) | Enterで同階層に項目追加、Tabで字下げ、bulletから集中、枝単位移動 | 行を最小の編集単位にし、bulletと開閉記号を別用途にする | P0 |
| [Dynalist Keyboard reference](https://help.dynalist.io/article/91-keyboard-shortcut-reference) | Tab/Shift+Tab、Undo/Redo、選択、ノート切替を体系化 | 文章入力と構造移動のキー体系を分離する | P0の基本、複数選択はP1 |
| [RemNote Outlines](https://help.remnote.com/en/articles/8196578-outlines-and-terminology) | 字上げ時の親子関係を保つ移動、折りたたみと構造の区別 | 枝全体を移動させ、並び順だけで親子関係を暗黙に変えない | P0 |
| [Tana Supertags](https://outliner.tana.inc/learn/features/supertags)・[Nodes and references](https://outliner.tana.inc/learn/features/nodes-and-references) | ノードに型とフィールドを与え、参照して再利用 | 段落と根拠URLの連結はノードをキーにする | P3候補、P0には不採用 |
| [WAI-ARIA treeview](https://www.w3.org/WAI/ARIA/apg/patterns/treeview/) | 選択中ツリーの矢印移動、左右展開、可視フォーカス | 選択中と編集中を明確に区別、通常Tabを奪わない | P0 |

**再リサーチでの反証**：「すべてを一つのノード型へ統合する」ことは必ずしも正解でない。既存ユーザーは独立した段落やURLの高速収集も行う。まず編集の軸をノードにし、既存の文・段落・URLのデータ契約は維持して、参照関係を後から追加する。

評価は競合資料・コード分析に基づく設計判断であり、実利用者を対象としたA/Bテスト結果ではない。

### ペルソナ対話の要旨

- **情報収集者**：「URL、断片メモを大量投入する時、毎回枝を決めるのは遅い。分類しなくても書ける未整理の入口は必要」
- **論理構造編集者**：「構造化中に別の入力欄へ移動したくない。行の編集と移動を一つの操作連鎖にしたい」
- **採択**：アウトライン本文を編集の主役としながら、別途「未整理のアイデアをすぐ書く」小さな収集欄を残す。両者の違いは保存型ではなく作業段階で表現する。

## 5. 実装したP0プロトタイプ

### 実装範囲

1. 各行の`textarea`を直接編集。Enterで同階層に次行を作り、即座にフォーカスを移す。Shift+Enterは改行。
2. 編集中だけTab/Shift+Tabで階層を変更。閲覧モードに戻すEsc、矢印による行移動、通常Tab移動。
3. 上下移動は子孫を含む枝単位。字上げは親の次の兄弟として配置して既存の親子関係を守る。
4. 100件までのスナップショット履歴で構造変更を多段Undo/Redo（サーバー同期なし）。
5. bulletでズーム、矢印記号で枝の折りたたみ。葉ノードをズームした場合も**その項目自身**を見出しとして編集できる。
6. 未整理の即時入力欄、選択ノードの参考パネル、320pxからのモバイル構造操作バー。
7. 試作専用localStorageキー`kakidas-p0-lab.v1`。既存DB・Supabaseとの接続はない。JSON出力と初期化ができる。

**今回入れていないもの**：既存memoへの取り込み、複数選択、ドラッグ＆ドロップ、項目削除の確定仕様、段落・URLとの永続的関係、クラウド同期、変更履歴の永続化、実機IME試験、認証。関連情報パネルは表示意図を示すためのスタブである。

### テスト結果の読み方

- ローカルChromiumの`page.set_content`を使う一連の自動検証で**8/8カテゴリ合格**。内容は30行連続入力、字下げ・字上げ、枝移動と2回Undo＋Redo、葉のズーム、IME合成イベント、未整理入力、6画面幅、閲覧モードのTab。
- この過程で**フォーカス移動がアニメーションフレームまで遅れる不具合**が発見され、入力欄生成直後に同期的にフォーカスを置くよう修正した。
- 合成IMEイベントは日本語IME実機の代わりにはならない。
- GitHub Actionsでは実際のHTTPオリジンを使い、ローカルストレージ再読み込みの継続性を別途検査する設計。
- 自動テストの操作時間を実際のユーザーの生産性の改善率と扱わない。

## 6. 正式版の設計判断とデータ移行

### 操作の状態遷移

```text
行内編集中 ─ Enter ─→ 次の行を作成して編集を継続
    │ Tab/Shift+Tab → 現在の枝を階層変更して編集を継続
    └ Esc ─→ 閲覧・選択モード ─ Arrow↑↓←→ ─→ 行／枝を移動・開閉
                                 └ Enter ─→ 行内編集
bulletクリック ─→ 集中表示（葉ノードも見出しを含める）
```

### 保存モデル

既存の`sentence`/`paragraph`/`word`を壊さず、アウトライン編集時の`sentence`では`parent_id`・`sort_order`を維持。移動は枝全体の表示順・親IDを原子的に書き込む。Undo/Redoの履歴は最初はタブ内、正式移行時はクラウド同期競合との整合を設計する必要がある。再編集後のredo破棄、権限／未送信操作の扱いを仕様化する。

段落・URLは次期追加の関連表（例：`entry_links(source_entry_id, target_entry_id, relation_type, created_at)`）で接続する案。ただし、これは仮説上のデータモデルであり、今のリポジトリに存在する表ではない。重複参照、削除時の孤児参照、権限制約を検証するまでは採用しない。

## 9. 次に実行する5タスク

1. **実ユーザーによる比較**：旧UIとP0で同じ30行の入力、5階層変更、枝移動、3回Undoを実施し、手数・時間・誤操作を記録。
2. **スマホ実機評価**：iPhone Safariでソフトキーボード表示時のツールバー、文字変換中Enter、スクロール、タップ領域を点検。
3. **React移植設計**：`OutlineList`に直接移植する部分と、`EntryComposer`から引き上げる責務を分ける。現行データ形式は変更しない。
4. **Undo・保存モデルの強化**：構造Undoの粒度と本文Undoの衝突を決め、IndexedDBでの原子更新・クラウド競合をテスト。
5. **本実装判断**：上記の比較で旧版より操作負荷が改善し、データ破損・誤操作がなければ本実装用PRを作成。未達ならP0へ戻す。

## 制約と未解決論点

P0は既存データを模しているが、そのスキーマを直接利用してはいない。変更履歴は同一ページのメモリ上のみで、ページ再読込するとUndo履歴は消える。UIにデータ関係を示す右パネルがあるが、現状は説明用で実データ参照ではない。複数選択、100項目超の性能、視覚・運動特性の異なるユーザーの評価は未実施。ここを解消せず本番移植したと主張しない。
